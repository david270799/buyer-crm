# CLAUDE.md — Buyer CRM

Главный файл контекста для Claude Code. Прочитайте его целиком перед работой, затем `HANDOFF.md`
(текущее состояние и следующие задачи). Подробные таблицы полей и правил —
[docs/architecture.md](docs/architecture.md), запуск на сервере — [docs/deploy.md](docs/deploy.md),
исходное ТЗ владельца — [docs/spec-original.md](docs/spec-original.md).

## 1. Что это и для кого

CRM для **байера**: он выкупает товары (в основном кроссовки) в Южной Корее для **одного постоянного
B2B-клиента**. Участников только два:

* **ADMIN / BUYER** — владелец CRM (он же наш собеседник). Управляет всем.
* **CLIENT** — один клиент. Только смотрит: заказы, статусы, фото, отправки, баланс, историю.
  У клиента в Telegram-группе есть **помощники**: они присылают заказы, но в CRM доступа не имеют.

Не SaaS, мультиклиентность не нужна, но код разбит на слои так, чтобы расширение было возможно.

Деньги: основная валюта **KRW**; баланс клиента дополнительно показывается в **USD** по курсу,
который задаёт админ (`krw_per_usd`). Баланс может быть отрицательным (долг клиента) — это нормально.
Время хранится в UTC, показывается по **Asia/Seoul**.

### Кто владелец и как с ним работать

* Пишет по-русски (иногда транслитом или голосом через распознавание), присылает скриншоты.
  **Отвечать по-русски, просто и по шагам** — он не программист (ставит сервер впервые).
* **Никогда не просить вставить в чат** токен бота, ключ Gemini, ключ Firebase, пароли.
  Ключи вводятся только на сервере: `deploy/setup.sh` спрашивает их со скрытым вводом, или `nano .env`.
* Пишущие изменения — коммитить и пушить после каждого законченного куска (сессии обрываются по лимиту).
* Решения, которые меняют деньги, баланс, прибыль, безопасность или могут потерять данные, — сначала
  спросить. Мелочи — решать самим безопасно и сообщать, что решили.

## 2. Состав системы

| Часть | Где | Что делает |
|---|---|---|
| Telegram-бот (группа + личка админа) | `backend/crm/bot` (aiogram 3, long polling) | принимает заказы по фото в группе, команды админа (`/buy`, `/cargo`, …), вопросы админу в личку, уведомления, ночные копии базы |
| HTTP API | `backend/crm/api/app.py` (FastAPI) | для Mini App: проверка Telegram `initData`, роли, JSON только через `domain/views.py` |
| Mini App клиента | `web/` (React + TS + Vite), `ClientApp.tsx` | только чтение: главная, заказы, отправки, баланс и история, уведомления |
| Mini App админа + веб-панель | `web/`, `AdminApp.tsx` | та же сборка; на широком экране — боковое меню и таблица заказов |
| Распознавание фото | `backend/crm/services/recognition.py`, `photo_recognition.py` | Gemini (REST `generateContent`) читает фото и подпись → бренд, модель, размер, ссылка; значок ✨ у поля «Бренд» в форме заказа Mini App (`POST /api/recognize`, только заполняет форму) |
| AI-ассистент админа | — | **ещё не сделан** (фаза 9 ТЗ: intent → validator → whitelist → service) |

Всё работает **одним процессом** `python -m crm.server`: API + статика Mini App (`web/dist`) + бот.
Один процесс — потому что long polling допускает только одного получателя обновлений, а SQLite —
одного писателя.

## 3. Стек

* **Backend:** Python 3.11+ (в Docker 3.12), aiogram 3, FastAPI + uvicorn, Pillow (фото), httpx (Gemini),
  python-dotenv, tzdata; `firebase-admin` — только для необязательного режима Firestore.
* **Хранилище:** SQLite (по умолчанию) через собственный document-store поверх in-memory движка;
  Firestore — опционально (`STORAGE=firestore`).
* **Frontend:** React 18, TypeScript 5.6, Vite 5, TanStack Query 5, react-router-dom 6 (`HashRouter`),
  lucide-react. Без UI-библиотек, свой CSS (`web/src/styles/app.css`, CSS-переменные, светлая/тёмная тема).
* **Инфраструктура:** Docker (multi-stage: node → python), docker compose + Caddy (автоматический HTTPS),
  GitHub Actions CI.
* **Тесты:** pytest (+ Firestore Emulator в CI), vitest; линтер/формат — ruff.

## 5. База данных

Исторически ТЗ было под **Firebase Firestore + Firebase Storage**. 28.09.2026 владелец решил перейти
на **SQL на своём сервере** — сейчас по умолчанию **SQLite** (`STORAGE=sqlite`), Firebase не нужен
(ни ключ сервисного аккаунта, ни Storage). Режим Firestore остался рабочим и покрыт тестами, но не
используется. Старых данных из прежнего Firestore в новой базе нет — начали с чистой базы (номера с N1).

### Как устроено хранение (SQLite)

* Модель данных **документная, как в Firestore**: коллекции → документы (JSON). Код пишет через
  порт `Database`/`Transaction` (`crm/storage/base.py`), поэтому бизнес-логика не знает, где лежат данные.
* `SqliteDatabase` держит все данные в памяти (движок `InMemoryDatabase`: чтения до записей,
  оптимистичные повторы, атомарные `create`/`update` — те же правила, что у Firestore) и **каждый
  коммит сначала пишет в SQLite** одной SQL-транзакцией (WAL, `synchronous=FULL`, `BEGIN IMMEDIATE`).
  Если запись на диск не удалась — изменение не применяется. При старте всё читается из файла.
* Транзакции выполняются по одной (`_tx_lock`) — один процесс, конфликтов нет.
* Файл-замок `crm.sqlite3.lock`: второй процесс CRM на ту же базу не стартует. `doctor` и копии
  открывают базу read-only и могут работать рядом с сервером.
* Таблица `documents(collection, id, data JSON, updated_at)`, служебная `meta`; представления
  `orders_v`, `transactions_v` для SQL-отчётов. Даты в JSON — `{"$dt": "<ISO>"}`.
* Файлы: `DATA_DIR/crm.sqlite3`, фото `DATA_DIR/media/` (WebP; отдаются по `/media/...`),
  копии `DATA_DIR/backups/crm-YYYYMMDD-HHMMSS.sqlite3.gz`. В Docker `DATA_DIR=/data` = том `crm_data`.

### Коллекции (одинаковы для SQLite и Firestore; все поля — в docs/architecture.md)

| Коллекция / документ | Смысл |
|---|---|
| `client_info/main_client` | клиент: `telegram_id`, `name`, `balance` (KRW), `balance_updated_at`. Создаётся `/setclient` с балансом 0 |
| `orders/N{n}` | заказ: статус, бренд/модель/размер, цены (`purchase_price`, `client_price`, `profit`), `charged_amount_krw`, `refunded_amount_krw`, `shipment_id`, фото, `source_url` (только админ), `client_comment` / `internal_comment`, `attention_required`, `purchases[]` (история закупок, только админ), `recognition` (что прочитал Gemini, только админ), временные метки и `created_by`/`updated_by` |
| `shipments/SHP-YYYY-NNN` | физическая отправка: `shipment_number` («Отправка #18»), трек, коробка, вес, `shipping_cost_krw`, `shipping_charged_krw`, фото, `order_ids[]` |
| `transactions/{id}` | ledger баланса, только добавление: `type` (`order_charge`, `order_refund`, `order_rebuy`, `order_discount`, `deposit`, `adjustment`, `shipping_charge`), `amount_krw` со знаком, `balance_before/after`, связи. ID детерминированные → идемпотентность |
| `profit_entries/{id}` | доп. прибыль админа (`/profit`, «Моя прибыль» в «Финансах»): `amount_krw`, `comment`; только админ, баланс клиента не меняет, входит в прибыль сводки |
| `settings/general` | `krw_per_usd` |
| `settings/security` | PIN админа для Mini App: `pin_hash` (PBKDF2, соль), `pin_length`; сам код не хранится. Экран PIN — только для админа, сброс `/pin off` |
| `settings/groups` | `chats` {id: название} — разрешённые группы, задаются `/setgroup` (плюс `ALLOWED_CHAT_IDS` из env) |
| `settings/notifications` | уведомления в личку: `recipient` (`off`/`admins`/`client`), `level` (`important`/`all`) |
| `counters/orders`, `counters/shipments` | `next_id`; увеличиваются только в транзакции; после удаления заказов номера возвращаются только с конца, не ниже `floor` (номера с историей денег) |
| `events/{id}`, `event_reads/tg:{id}` | лента событий для клиента (история заказа, колокольчик) + outbox доставки в Telegram; отметка «прочитано» |
| `intake/tg{chat}_{message}` | какое сообщение Telegram стало каким заказом (одно сообщение → максимум один заказ) |
| `reactions/tg{chat}_{message}` | какая реакция поставлена на фото заказа (`status`, `emoji`, `error`); отказ Telegram не повторяется до смены статуса |
| `audit_logs/{id}` | кто, откуда, что изменил (`before`/`after`); никогда не удаляется |

Статусы заказа: `new` → `bought` → `warehouse` → `cargo` → `delivered`, отдельно `cancelled`
(в интерфейсе: Новый заказ → Выкуплен → На складе → Отправлен → Доставлен / Отменён).

## 6. Как работает бот

* **Роли:** админ — `ADMIN_TELEGRAM_IDS`; клиент — `client_info/main_client.telegram_id` (задаётся
  `/setclient` ответом на сообщение клиента или `/setclient ID Имя`). Роль проверяется в middleware
  бота и ещё раз внутри сервиса.
* **Заказы по фото** (`bot/handlers/intake.py` → `services/intake_service.py`):
  * одно сообщение с фото = один заказ (альбомы не собираются); ответы на сообщения — не заказы;
  * в группе заказ принимается **от любого участника, кроме админа** (клиент и помощники;
    `Actor.order_sender` даёт право только на приём заказа); в личке с ботом — от клиента или админа;
  * шаги: скачать → квадрат 1:1 на белом фоне → WebP ≤ ~500 КБ + миниатюра → Gemini → сохранить фото →
    создать заказ `new` (без цен, баланс не трогается) в одной транзакции с `intake`-документом;
  * **в группу бот не пишет ничего** — только ставит **реакцию** на фото заказа по статусу
    (`services/reactions.py` + `bot/reactions.py`): «Новый» — без реакции, выкуплен 👍, на складе 🏠→👌,
    отправлен ✈️→🕊, доставлен ✅→💯 (выбор владельца; ботам доступны только стандартные реакции
    Telegram, поэтому после стрелки — замена), отменён/удалён — реакция снимается. Синхронизатор
    сравнивает заказы с `reactions/tg{chat}_{message}` после каждого коммита и раз в 5 минут.
    Если есть вопрос (модель не распознана, нет размера, не похоже на
    товар, ошибка) — админу в личку фото (по `file_id`), вопрос, подпись, отправитель, ссылка на сообщение;
  * до 3 фото обрабатываются параллельно, но номера идут в порядке отправки (цепочка на чат
    регистрируется до первого `await`);
  * `/add` ответом на фото — принять как заказ принудительно; повторная доставка апдейта ничего не дублирует;
  * бот принимает заказы только после добавления в группу, истории не импортирует;
  * добавил бота не админ → бот выходит и сообщает админам; для группы нужен выключенный Privacy Mode.
* **Команды админа:** `/buy`, `/cancel`, `/rebuy`, `/status`, `/delete`, `/cargo`, `/shipcost`, `/deposit`,
  `/adjust`, `/profit`, `/rate`, `/notify`, `/pin`, `/backup`, `/add`, `/setclient`; общие: `/order`, `/balance`, `/history`,
  `/shipments`, `/shipment`, `/whoami`, `/help` (таблица — в README). Ответы на `/add`, `/setclient`
  в группе уходят админу в личку, команда удаляется из группы.
* **Уведомления в личку** (`bot/notifier.py`): outbox — события пишутся с `delivery: pending` в той же
  транзакции; отправитель просыпается после коммита (`after_commit`) и раз в 5 минут, до 5 попыток,
  кнопка «Открыть в CRM» (`?open=order:N5`). По умолчанию выключены (`/notify` или «Настройки»).
* **Ночная копия:** в 04:00 по Сеулу копия базы (gzip) уходит админам в личку (`BACKUP_TO_TELEGRAM`); `/backup` — копия сразу, только спросившему админу.
* При старте бот предупреждает в логах: Privacy Mode включён, нет ключа Gemini, нет админов.

## 7. Как работают Mini App (клиент и админ)

* Одна сборка `web/dist`, отдаётся тем же сервером. Роутинг — **`HashRouter`** (`#/orders/N5`), чтобы
  не нужны были серверные маршруты. Telegram кладёт параметры запуска в hash (`#tgWebAppData=…`) —
  маршрут `*` переводит на `/`. Ссылки из уведомлений: `?open=order:N5 | shipment:<id> | notifications`.
* **Вход:** каждый запрос — `Authorization: tma <initData>`; сервер проверяет HMAC по токену бота и
  свежесть (`INIT_DATA_MAX_AGE_HOURS`, 24 ч). `initDataUnsafe` не используется. Демо-вход
  (`Authorization: demo admin|client`) работает **только** в `--demo`.
* **Клиент — только чтение.** Все `POST/PATCH/PUT` требуют админа; ответы строятся только через
  `domain/views.py`. Клиент никогда не видит: закупочную цену, прибыль, `internal_comment`,
  ссылки на магазины (`source_url`, `purchases[]`), данные распознавания.
* Админ: сводка, заказы (карточки на телефоне, таблица на компьютере, фильтры, массовые действия),
  создание заказа, отправки (выбор заказов → модалка), финансы (пополнение/корректировка с ключом
  идемпотентности), настройки (курс, уведомления). Помощники клиента получают «нет доступа».
* Загрузка: `index.html` сразу показывает индикатор (без блокирующих внешних ресурсов: шрифты
  не блокируют отрисовку, `telegram-web-app.js` — `defer`), через 8 с — кнопка «Обновить»;
  ошибки рендера ловит `ErrorBoundary` (текст ошибки + «Обновить», меню остаётся рабочим).
  `index.html` отдаётся с `Cache-Control: no-cache`, файлы `/assets/*` — `immutable`.

## 8. Правила денег и безопасности (не нарушать)

1. Баланс меняет **только** `BalanceLedger.apply` — вместе с записью в `transactions` в одной транзакции.
2. `/buy` списывает `client_price` один раз (проверка статуса и `charged_amount_krw` + `create` записи
   `order_charge_N…`); `/cancel` возвращает ровно `charged_amount_krw` один раз.
3. Перезаказ и изменение стоимости доставки двигают только **разницу**. После отправки (`cargo`/`delivered`)
   отмены и возвратов нет.
4. Деньги не двигаются по догадке: нет `charged_amount_krw` → считается, что ничего не списано.
5. Статусы, двигающие деньги (`bought`, `cancelled`, `new`), ставятся только своими командами.
6. Пополнения/корректировки идемпотентны (ID сообщения Telegram или ключ формы Mini App).
7. **AI (Gemini) никогда сам не:** удаляет коллекции, массово удаляет документы, меняет Telegram ID,
   правила безопасности или учётные данные, выполняет произвольные запросы из текста пользователя или
   произвольный код, меняет баланс вне контролируемой финансовой операции, меняет финансовую историю,
   удаляет audit-логи. Gemini не выдумывает данные при низкой уверенности. Сейчас Gemini только читает
   фото и подпись; будущий ассистент — только через whitelist действий с подтверждением записи.
8. Секреты только в `.env` / секретах сервера; `.gitignore` не пропускает `.env`, ключи и `data/`.

## 9. Ключевые решения и почему

| Решение | Почему |
|---|---|
| **SQLite на своём сервере вместо Firebase** (по умолчанию) | сервер всё равно нужен (бот и API работают постоянно); у владельца VPS с диском 30–40 ГБ; нет лимитов и счетов Firebase; один файл — простые копии. In-memory движок сохранил семантику транзакций Firestore, поэтому бизнес-логику не переписывали; Firestore остался как опция |
| Данные в памяти + запись каждого коммита в SQLite | данных мало (сотни заказов, владелец: «до 1000 не доходит») — всё помещается в память, чтение мгновенное, а надёжность даёт синхронная запись на диск до применения |
| Номера заказов **N1, N2…** с заглавной N, с единицы | просьба владельца; в старом Firestore были `n1…n125`, но база новая. Ввод принимает `5`, `n5`, `N05`, `#5` |
| Один процесс API + бот | long polling и SQLite допускают только одного получателя / писателя |
| Ночная копия базы админам в Telegram | копия вне сервера без настройки облака; фото в копию не входят (их можно прислать заново) |
| Доставка **списывается с баланса** | решение владельца |
| Перезаказ с разницей в цене, история видна клиенту, ссылка магазина — только админу | магазины отменяют выкупленные заказы; владелец покупает в другом месте по другой цене |
| После отправки возвратов нет | решение владельца: доставленный заказ закрыт |
| Удаление заказов (`/delete`, Mini App): любой, в том числе отправленный (29.09 владелец снял ограничение); отовсюду, из `order_ids` отправки тоже; списанное возвращается, клиенту строки удалённого заказа не показываются; номера — только с конца | владелец: ошибочно добавленные заказы; номер с историей денег не выдаётся снова (ID записей `order_charge_N…` детерминированные) |
| Скидка на выбранные заказы (%, `OrderService.discount`): только до отправки, без округления, оплаченным — возврат разницы записью `order_discount_{N}_{ключ}` на каждый заказ; `orders.discounts[]` — история (ключ формы → повтор ничего не меняет) | владелец: «даю 10% за большую покупку»; клиенту приятно видеть скидку; запись на заказ сохраняет нулевую сумму при отмене/удалении |
| PIN-код на вход админа в Mini App (экран с круглыми кнопками, «разблокировано» до закрытия Mini App — `sessionStorage`) | владелец: «формальность», чтобы посторонний с его телефоном не увидел CRM; это экран, а не защита API — API по-прежнему проверяет Telegram `initData` |
| Колокольчик: «важные» / «все» | владелец: важные — отмена, перезаказ, отправка и т. п.; обычные — всё остальное, включая выкуп |
| Уведомления в личку: выкл / только админам / клиенту; по умолчанию выкл | сначала проверить на себе, потом включить клиенту |
| Бот молчит в группе, вопросы — админу в личку | просьба владельца: в группе клиент и его помощники |
| Реакция на фото заказа по статусу | владелец: клиент смотрит в группу, реакция показывает, что заказ выкуплен/пришёл/отправлен/доставлен |
| Заказы от любого участника группы, Mini App — только клиенту | помощники присылают заказы, но не должны видеть CRM |
| Одно фото = один заказ, без альбомов, без импорта истории | так владелец получает заказы; принимаются только сообщения после добавления бота |
| Фото: квадрат 1:1, белые поля, без обрезки и растягивания, WebP 80–500 КБ, без цветокоррекции | владелец разрешил до 500 КБ (в ТЗ было 80–120 КБ); одинаковые карточки |
| Gemini: ссылка — только из подписи, размер — из подписи или явно на фото, при уверенности < 0.6 бренд/модель пустые, «не товар» только при ≥ 0.8 | ТЗ: не выдумывать; ссылки из текста Gemini в клиентские поля не попадают |
| Старые заказы не импортируются | владелец добавит только заказы последней недели (в пути) обычным путём; режим «без повторного списания» не нужен |
| `HashRouter` | Mini App — статика на том же сервере, без серверных маршрутов |
| Docker + Caddy, `DOMAIN` необязателен | HTTPS автоматически; без домена бот работает, Caddy отдаёт HTTP на :80 |
| Сервер: корейский VPS, по словам владельца (29.09) **1 ГБ RAM** (а не 2 ГБ, как считалось), Ubuntu 24.04, «OS만 설치», порты 22/80/443 | на 1 ГБ сборка образа идёт только со swap (`deploy/setup.sh` его создаёт); большие фото на сервере не разжимать — лимит 20 МБ / 50 Мп не поднимать; APM поставил бы Apache на 80-й порт и конфликтовал бы с Caddy |

## 10. Команды разработки

```bash
# backend
cd backend
python -m venv .venv && . .venv/bin/activate && pip install -r requirements-dev.txt
ruff check crm tests && ruff format --check crm tests
python -m pytest -q                                   # memory + sqlite (эмулятор пропускается)
firebase emulators:exec --only firestore --project demo-buyer-crm "cd backend && python -m pytest -q"  # + Firestore
python -m crm.server --demo                           # демо без ключей: http://localhost:8080
python -m crm.tools.doctor                            # проверка настроек (read-only)

npm run typecheck && npm test && npm run build        # сборка в web/dist (её отдаёт сервер)
CRM_BACKEND=http://localhost:8080 npm run dev         # dev-сервер с прокси на API

# сервер (Docker)

docker compose logs -f crm
docker compose exec crm python -m crm.tools.doctor
```

## 11. Соглашения

* Тексты для пользователя (бот, Mini App, ошибки) — **по-русски**; код, имена и комментарии — по-английски.
* Хендлеры бота и эндпоинты API тонкие: разбор ввода → `asyncio.to_thread(service.method, actor, …)` →
  форматирование. Бизнес-логика — только в `services/`, правила видимости — только в `domain/views.py`.
* Документы не перезаписываются целиком (`update`, а не `set`), чужие поля сохраняются.
* Любая пишущая операция — транзакция + audit log; где касается клиента — событие в той же транзакции.
* Ошибки для пользователя — понятный текст (`CRMError.user_message`), без трассировок.
* Каждый тест с хранилищем идёт на трёх бэкендах (фикстура `db`: memory, sqlite, emulator).
  CI должен быть зелёным; перед пушем — ruff, pytest, `npm run typecheck && npm test`.
* Идентификаторы моделей ИИ в коммиты и код не писать.

### Git, версии и CHANGELOG (постоянные правила владельца)

* **Один коммит — одно изменение.** Каждая фича, фикс или правка — отдельным коммитом. Сообщение
  коммита — **по-русски**: первая строка кратко говорит, что изменено; в теле — зачем (какую проблему
  решает, о чём просил владелец). Не смешивать в одном коммите несвязанные правки.
* **Новые функции — в отдельной ветке.** В `main` сливать только после того, как владелец подтвердит,
  что всё работает. Без подтверждения в `main` ничего не вливать; сервер обновляется с `main`.
* **Теги версий.** Когда владелец говорит, что версия стабильная, ставить на коммит в `main`
  аннотированный тег `v1.0`, `v1.1`, `v1.2` … (следующий номер по порядку; `v2.0` — только по
  решению владельца) и пушить тег (`git push origin vX.Y`). Без слов владельца тег не ставить.
* **CHANGELOG.md.** Каждое изменение сразу записывать в раздел «Не выпущено» (в том же коммите,
  что и само изменение): дата и список правок простыми словами. При теге раздел переименовывается
  в `## vX.Y — ДД.ММ.ГГГГ`, сверху открывается новый пустой «Не выпущено».

## 12. Грабли, на которые уже наступали

* Пустая строка `DATA_DIR=` в `.env` перекрывала `/data` образа → база создавалась вне тома и CRM падала.
  Поэтому compose задаёт `DATA_DIR: /data` в `environment`, а в `.env.example` строка закомментирована.
* Новые ключи Gemini начинаются с **`AQ.`** (старые — `AIza`); передаются заголовком `x-goog-api-key`.
  Не валидировать ключ жёстким регулярным выражением.
* Без `Cache-Control` Telegram показывал старую копию `index.html` с несуществующими скриптами →
  пустой экран до Reload (исправлено; см. §7).
* `useEffect(() => window.scrollTo(0, 0), …)` в Telegram возвращал не `undefined`, и React вызывал это
  как функцию очистки → «n is not a function» при каждом переходе между разделами. Эффекты писать
  только с телом в фигурных скобках, если не возвращается функция очистки.
* Администратор группы с «Анонимностью» пишет от имени `1087968824` — бот не видит его ID. Нужно выключить.
* Privacy Mode бота в @BotFather должен быть выключен, иначе бот не видит фото в группе.
* Один токен — один работающий бот: при запуске второго экземпляра (например, на компьютере) — конфликт polling.
* В `pkill -f` не использовать шаблон, совпадающий с текстом самой команды (убивает собственный shell).
* В облачной песочнице Claude сборка Docker-образа падает на pip/npm из-за TLS-прокси — это особенность
  среды, не проекта (CI собирает образ нормально).

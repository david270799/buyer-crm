# Архитектура Buyer CRM

## Слои

```
Telegram bot ─┐
Mini App API ─┤  crm/api (клиент + админ, та же панель на компьютере)
AI assistant ─┘  (Phase 9)  ──────▶ ┌────────────┐     ┌──────────────┐     ┌─────────────┐
                                    │  services  │ ──▶ │ repositories │ ──▶ │   storage   │ ──▶ Firestore
                                    └────────────┘     └──────────────┘     └─────────────┘
                                     бизнес-правила      маппинг              Database-порт:
                                     роли, транзакции    документ ↔ модель    Firestore | InMemory
```

| Пакет | Что внутри | Что запрещено |
|---|---|---|
| `crm/domain` | статусы, ID, деньги, модели, правила видимости (`views.py`) | импорт Firestore и Telegram |
| `crm/storage` | порт `Database`/`Transaction`, `FirestoreDatabase`, `InMemoryDatabase` | бизнес-логика |
| `crm/repositories` | имена коллекций, чтение/запись конкретных документов | решения о деньгах и статусах |
| `crm/services` | все операции CRM: `OrderService`, `ShipmentService`, `FinanceService`, `BalanceLedger`, `RoleResolver` | Telegram-специфика |
| `crm/bot` | aiogram: middleware ролей, парсинг аргументов, тексты ответов, тонкие хендлеры | прямой доступ к Firestore |
| `crm/api` | FastAPI: проверка Telegram `initData`, роли, JSON только из `domain/views` | бизнес-логика |
| `web/` | Mini App (React + TS): режим клиента и админа, адаптив телефон/компьютер | доступ к Firestore в обход API |

Хендлер: разобрать аргументы → `await asyncio.to_thread(service.method, actor, …)` → отформатировать ответ.
Firestore-клиент синхронный, поэтому сервисы вызываются в отдельном потоке и не блокируют event loop.

Mini App и AI-ассистент вызывают **те же сервисы**. Например, форма «Создать отправку»
в Mini App и команда `/cargo` вызывают один и тот же `ShipmentService.ship_orders`.

### Mini App и API

* Вход: каждый запрос несёт `Authorization: tma <initData>`. Сервер проверяет HMAC-подпись
  по токену бота и свежесть `auth_date` (по умолчанию 24 ч), затем определяет роль.
* Клиентские эндпоинты только читают. Все изменения (`POST/PATCH/PUT`) требуют роль админа;
  роль ещё раз проверяется в сервисе.
* Ответы строятся только из `crm/domain/views.py` — там единственный список полей, которые видит клиент.
* Формы пополнения и корректировки отправляют ключ идемпотентности: двойное нажатие не проводит операцию дважды.
* Фото: `POST /api/images` → WebP ≤ 1280 px (~80–120 КБ) + миниатюра 400 px, Firebase Storage
  с token-URL. В Firestore хранятся только ссылки.
* Демо (`python -m crm.server --demo`): in-memory данные, вход без Telegram через выбор роли —
  этот способ входа существует только в демо-режиме.

## Модель данных Firestore

Существующие документы не мигрируются. Код только добавляет новые поля и никогда
не перезаписывает документ целиком (`update`, а не `set`), поэтому чужие поля сохраняются.

### `orders/{nN}`

| Поле | Кто пишет | Смысл |
|---|---|---|
| `order_id`, `status`, `purchase_price`, `client_price`, `profit`, `cargo_code` | было | как раньше; `profit = client_price − purchase_price` |
| `charged_amount_krw` | **новое** | сколько по заказу сейчас списано с баланса. `/buy` ставит `client_price`, `/cancel` ставит 0 |
| `refunded_amount_krw` | новое | сколько вернул `/cancel` |
| `shipment_id` | новое | ID отправки |
| `bought_at`, `warehouse_at`, `cargo_at`, `delivered_at`, `cancelled_at`, `created_at`, `updated_at` | новое | UTC Timestamp |
| `created_by`, `updated_by` | новое | `tg:<telegram id>` |
| `brand`, `model`, `size`, `photo_url`, `thumbnail_url`, `source_url`, `source_chat_id`, `source_message_id`, `client_comment`, `internal_comment`, `attention_required` | новое, по мере фаз | см. ТЗ |
| `purchases[]`, `rebuy_count` | новое, только админ | все закупки заказа (первый выкуп и каждый перезаказ: цена, магазин, дата, `replaced_at`) |

### `shipments/{SHP-YYYY-NNN}`
`shipment_id`, `shipment_number` (сквозной номер «Отправка #18»), `tracking_code`, `box_number`,
`weight_kg`, `shipping_cost_krw`, `shipment_date`, `photo_url`, `order_ids[]`, `comment`,
`shipping_charged_krw` (сколько за доставку сейчас списано), `shipping_charge_seq`,
`created_at/by`, `updated_at/by`. Год в ID берётся по времени Сеула.

### `transactions/{id}`: ledger баланса (только добавление)
`transaction_id`, `type` (`order_charge` | `order_refund` | `order_rebuy` | `deposit` | `adjustment` | `shipping_charge`),
`amount_krw` (со знаком), `balance_before`, `balance_after`, `order_id`, `shipment_id`, `comment`,
`created_at`, `created_by`, `source`.

ID детерминированные там, где это даёт идемпотентность:
`order_charge_n5`, `order_refund_n5`, `order_rebuy_n5_1` (…`_2` при следующем перезаказе),
`shipping_charge_SHP-2026-001_1` (…`_2` при изменении стоимости),
`deposit_tg<chat>_<message>`, `adjustment_tg<chat>_<message>`, `deposit_ma-<ключ формы Mini App>`.

### Прочее
* `client_info/main_client`: `telegram_id`, `name`, `balance` (KRW, может быть < 0). Добавляется `balance_updated_at`.
* `settings/general`: `krw_per_usd`, `updated_at`, `updated_by`.
* `counters/orders.next_id`, `counters/shipments.next_id`: создаются автоматически при первом использовании
  (для заказов `next_id = max(nN) + 1`, т. е. `n126`).
* `audit_logs/{id}`: `actor`, `source`, `action`, `entity_type`, `entity_id`, `before`, `after`, `timestamp`.
* `events/{id}`: лента для клиента (история заказа и колокольчик): `type`, `important`, `title`, `body`,
  `order_ids[]`, `shipment_id`, `amount_krw`, `created_at`, `actor`. Пишется в той же транзакции, что и изменение.
* `event_reads/{tg:<id>}`: `seen_at` — когда пользователь последний раз открывал уведомления.
* `settings/notifications`: `recipient` (`off` | `admins` | `client`), `level` (`important` | `all`),
  `since`, `last_sent_at`, `last_error`, `last_error_at`.

### Уведомления

Событие создаётся только из бизнес-операции и только с безопасным для клиента текстом (без закупки,
прибыли и внутренних комментариев). Правило важности — `crm/domain/events.py`:

| Важные | Обычные («Все») | Не создают событий |
|---|---|---|
| перезаказ, отмена, отправка отправлена, «требуется внимание», изменение стоимости доставки, корректировка баланса | новый заказ, выкуп, прибыл на склад, доставлен, комментарий, изменение трека/комментария/фото отправки, пополнение, курс | правка бренда, модели, размера, фото, ссылки, внутреннего комментария |

Запросы ленты используют только одиночные индексы (`created_at`, `order_ids`) — составные индексы
в Firestore разворачивать не нужно.

### Уведомления в Telegram (личка)

Тот же текст, что в колокольчике, бот отправляет в личку. Настройка — в Mini App («Настройки») или
командой `/notify`: кому — выключены / только админам (проверка) / клиенту; что — важные / все.
По умолчанию выключены.

* **Outbox.** Каждое событие создаётся с `delivery: "pending"` в той же транзакции. Отправитель
  (`crm/bot/notifier.py`, работает рядом с polling в процессе бота) берёт ожидающие события, отправляет
  и записывает результат в событие: `sent` / `skipped` / `failed`, `delivered_to[]`, `delivery_attempts`.
  Перезапуск не теряет и не дублирует уведомления (при сбое между отправкой и записью возможен один повтор).
* **Когда.** Сразу после коммита транзакции с событием (`Transaction.after_commit`) и раз в 5 минут —
  для повторов и событий, записанных в другом процессе.
* **Что не отправляется** (`skipped`): уведомления выключены; событие ниже выбранного уровня; событие
  старше момента, когда сменили получателя (включение не рассылает накопленное); старше суток;
  у клиента нет `telegram_id`.
* **Ошибки.** Нет связи / 5xx — до 5 попыток при следующих проходах. Бот заблокирован или получатель ни
  разу не открыл бота (Telegram не даёт боту писать первым) — `failed` сразу; причина видна в настройках.
* **Кнопка «Открыть в CRM»** (если задан `MINI_APP_URL`) открывает Mini App на заказе, отправке или
  ленте: `?open=order:n5` / `shipment:<id>` / `notifications`. Если Telegram отклонит кнопку,
  сообщение уходит без неё.
* Одновременно может работать только один процесс бота (long polling), значит и один отправитель.

## Финансовые инварианты

1. **Баланс меняет только `BalanceLedger.apply`.** Он пишет новый баланс и запись в `transactions`
   в той же транзакции, поэтому `balance = начальный баланс + Σ amount_krw` всегда.
2. **`/buy` списывает один раз.** Внутри одной транзакции проверяется статус заказа и `charged_amount_krw`:
   * `new` и ничего не списано → списание;
   * уже выкуплен с теми же ценами → «уже выкуплен», ничего не меняется;
   * уже выкуплен с другими ценами → отказ (изменение цены станет отдельной операцией);
   * вторая линия защиты: запись `order_charge_nN` создаётся через `create`, и второе списание
     физически невозможно, даже если статус заказа сбросить вручную в консоли.
3. **`/cancel` возвращает ровно `charged_amount_krw` и обнуляет его**, поэтому повторный `/cancel` возвращает 0.
4. **Нет частичных операций.** Заказ, баланс, ledger и audit пишутся одним commit;
   при конфликте с параллельной операцией транзакция целиком повторяется на свежих данных.
   Это проверено тестами с параллельными потоками на Firestore Emulator.
5. **Статусы, которые двигают деньги, ставятся только своими командами.** `/status` не умеет
   `bought`/`cancelled`/`new`.
6. Пополнение и корректировка идемпотентны: из Telegram — по ID сообщения, из Mini App — по ключу формы.
7. **Доставка списывается с баланса.** В отправке хранится `shipping_charged_krw`; новая стоимость
   списывает или возвращает только разницу, поэтому повторное сохранение той же суммы ничего не меняет.
8. **Перезаказ двигает только разницу.** Если магазин отменил выкупленный заказ и товар куплен в другом
   месте, новая цена для клиента заменяет старую, а с баланса списывается или возвращается
   `новая цена − уже списанное` (одна запись `order_rebuy`). Повтор того же перезаказа ничего не меняет.
   Перезаказ возможен до отправки (`bought`/`warehouse`, не в отправке).
9. **После отправки денег не возвращают.** Заказ в `cargo`/`delivered` не отменяется и не перезаказывается
   (решение владельца: доставленный заказ закрыт).
10. **Деньги не двигаются по догадке.** Если у заказа нет `charged_amount_krw` (например, документ введён
    вручную в консоли Firebase), считается, что ничего не списано: `/cancel` вернёт 0, `/buy` откажет.
    `python -m crm.tools.doctor` показывает такие заказы.

## Производительность

Заказов — сотни (владелец: меньше тысячи). Список, фильтры и поиск в Mini App работают по полному
списку заказов, который сервер держит в памяти до 60 секунд и сбрасывает после любой записи через CRM.
Правки, сделанные вручную в консоли Firebase, появляются в течение минуты.

## Решения, принятые по умолчанию (безопасные)

| Ситуация | Поведение сейчас |
|---|---|
| `/buy` уже выкупленного заказа с другой ценой | отказ с подсказкой использовать перезаказ |
| `/buy` отменённого заказа | отказ |
| `/cancel` заказа в статусе `cargo`/`delivered` или внутри отправки | отказ: после отправки денег не возвращают |
| Статус доставленного заказа | админ может исправить ошибочно поставленный статус; денег это не касается |
| `/status warehouse/delivered` для заказа в статусе `new` | пропуск: сначала `/buy` |
| `/status cargo` без отправки | пропуск: используйте `/cargo` (он создаёт shipment) |
| `/cargo` с трек-номером, который уже есть | заказы добавляются в существующую отправку, повтор команды ничего не меняет |
| `/cargo` для заказа из другой отправки | пропуск с причиной (перенос между отправками появится позже) |
| Стоимость доставки в shipment | **списывается с баланса** (решение владельца); изменение — только разница |
| Цена после выкупа | меняется только перезаказом (с разницей через баланс); у «Нового» заказа — простым редактированием |
| Ответы бота в группе | всегда с клиентской видимостью: закупка, прибыль, ссылка на магазин (`source_url`, в том числе в истории закупок) и `internal_comment` показываются только в личке админа и в админской Mini App |
| Трек-номер | приводится к верхнему регистру: латиница, цифры, дефис |
| Лимиты | ≤ 100 заказов за команду; ≤ ₩1 000 000 000 за операцию; курс 100–10 000 |

## Открытые вопросы (нужно решение владельца)

Решено: доставка списывается с баланса; перезаказ с разницей по цене; после отправки возвратов нет;
старых данных нет — в CRM добавляются только текущие заказы, обычным путём (отдельный «архивный»
режим не нужен); ссылки на магазины видит только админ; уведомления в личку — да.

Остаются:

1. **Комментарии корректировок видит клиент** — нужен ли отдельный внутренний комментарий?
2. **Тестовые данные.** Сейчас всё на этапе проверки. Перед запуском с клиентом их нужно убрать —
   проще всего проверять на отдельном Firebase-проекте, а рабочий начать чистым.
